The Answer Protocol (TAP)
Un protocole de communication pour donjons multijoueurs (MUD) fondé sur TCP

Statut de ce document

1. Introduction

The Answer Protocol (TAP) est un protocole de couche application fondé sur TCP, conçu pour les environnements de donjons multijoueurs (MUD) en temps réel. Ce protocole permet à plusieurs clients de se connecter à un monde virtuel partagé dans lequel ils peuvent interagir avec l’environnement, communiquer avec d’autres joueurs et participer à un jeu collaboratif.

TAP fournit une interface de commandes textuelle simple avec transmission asynchrone des événements, ce qui le rend adapté aux interfaces en ligne de commande comme aux interfaces graphiques. Le protocole privilégie la simplicité, l’extensibilité et les capacités d’interaction en temps réel.

1.1 Terminologie des exigences

Les mots-clés « MUST » (DOIT), « MUST NOT » (NE DOIT PAS), « REQUIRED » (OBLIGATOIRE), « SHALL » (DOIT), « SHALL NOT » (NE DOIT PAS), « SHOULD » (DEVRAIT), « SHOULD NOT » (NE DEVRAIT PAS), « RECOMMENDED » (RECOMMANDÉ), « MAY » (PEUT) et « OPTIONAL » (FACULTATIF) utilisés dans ce document doivent être interprétés conformément à la RFC 2119.

1.2 Terminologie

  • Client : Une application qui se connecte à un serveur TAP
  • Serveur : L’implémentation du protocole TAP qui gère le monde virtuel
  • Joueur : Un client connecté dont l’identité est établie
  • Salle (Room) : Un lieu distinct dans le monde virtuel
  • Événement : Un message asynchrone envoyé par le serveur au client
  • Ressource : Un objet, un personnage non-joueur (PNJ, ou NPC en anglais) ou un autre élément interactif du monde

2. Présentation du protocole

TAP fonctionne sur des connexions TCP à l’aide de messages organisés en lignes et encodés en UTF-8. Chaque message se termine par un unique caractère de saut de ligne (0x0A). Le protocole suit un modèle hybride de requête-réponse avec transmission asynchrone des événements.

2.1 Caractéristiques du protocole

  • Transport : TCP (Transmission Control Protocol, protocole de contrôle de transmission)
  • Encodage : UTF-8
  • Délimiteur de messages : Saut de ligne (LF, 0x0A)
  • Modèle de connexion : Connexions persistantes
  • Flux de messages : Bidirectionnel avec événements asynchrones

2.2 Machine à états du protocole

Les connexions TAP passent par les états suivants :

  1. DISCONNECTED: Aucune connexion TCP établie
  2. CONNECTED: Connexion TCP établie, en attente d’authentification
  3. AUTHENTICATED: Identité du joueur établie, prêt à recevoir des commandes
  4. TERMINATED: Connexion fermée proprement ou à la suite d’une erreur

3. Gestion des connexions

3.1 Établissement de la connexion

Les clients DOIVENT établir une connexion TCP avec le serveur avant d’envoyer tout message TAP. Une fois la connexion TCP établie, le client DOIT envoyer une commande CONNECT pour établir l’identité du joueur.

Syntaxe ABNF :
connection-sequence = tcp-connect connect-command
tcp-connect = ; Établissement standard de la connexion TCP en trois étapes
connect-command = "CONNECT" SP username CRLF

3.2 Message d’accueil initial

Une fois la connexion TCP établie, le serveur DOIT envoyer un message d’accueil initial pour indiquer la version du protocole :

Serveur → Client : OK hello proto=1

3.3 Processus d’authentification

Après avoir reçu le message d’accueil, le client DOIT envoyer une commande CONNECT pour établir l’identité du joueur. Le serveur DOIT vérifier que le nom d’utilisateur demandé est unique parmi les connexions actives.

Serveur → Client : OK hello proto=1
Client → Serveur : CONNECT alice
Serveur → Client : OK connected

Si le nom d’utilisateur est déjà utilisé, le serveur DOIT répondre par une erreur :

Client → Serveur : CONNECT alice
Serveur → Client : ERR 201 NAME_IN_USE

3.3 Fermeture de la connexion

Les connexions PEUVENT être fermées proprement à l’aide de la commande QUIT ou brutalement en raison des conditions du réseau. Les serveurs DOIVENT gérer les deux situations et nettoyer correctement l’état du joueur.

4. Format des messages

4.1 Structure générale des messages

Tous les messages TAP suivent un format uniforme :

Syntaxe ABNF :
message = command-line / response-line / event-line
command-line = command-name [SP arguments] LF
response-line = ("OK" / error-response) [SP response-data] LF
event-line = "EVT" SP event-type SP event-data LF
command-name = 1*ALPHA
arguments = 1*VCHAR
error-response = "ERR" SP error-code SP error-message
error-code = 3DIGIT
event-type = 1*ALPHA
event-data = 1*VCHAR

4.2 Messages de commande

Les messages de commande sont envoyés du client au serveur et se composent d’un nom de commande suivi d’arguments facultatifs. Les noms de commande ne sont pas sensibles à la casse.

4.3 Messages de réponse

Les messages de réponse sont envoyés du serveur au client en réponse aux messages de commande. Les réponses commencent par « OK » en cas de succès ou « ERR » en cas d’échec.

4.4 Messages d’événement

Les messages d’événement sont des notifications asynchrones envoyées du serveur au client. Ils commencent par « EVT », suivi d’un type d’événement et des données associées.

5. Spécifications des commandes

5.1 Commandes de base

5.1.1 Commande CONNECT

Syntaxe : CONNECT <username>

Objectif : Établir l’identité du joueur pour la session

Réponses :

  • OK connected - Authentification réussie
  • ERR 201 NAME_IN_USE - Nom d’utilisateur déjà utilisé

5.1.2 Commande LOOK

Syntaxe : LOOK

Objectif : Récupérer l’état de la salle actuelle au format JSON

Réponse : OK <json-data>

Structure JSON :

{
  "room": {
    "id": "room.identifier",
    "name": "Room Display Name",
    "description": "Room description text",
    "exits": {
      "north": "room.north_id",
      "south": "room.south_id"
    }
  },
  "players": ["username1", "username2"],
  "items": ["item.id1", "item.id2"],
  "npcs": ["npc.id1", "npc.id2"]
}

Exemple :

Client → Serveur : LOOK
Serveur → Client : OK { "room": { "id": "loc.bakery", "name": "Village Bakery", "description": "A warm bakery filled with the scent of fresh bread.", "exits": {"south": "loc.square"} }, "players": ["alice"], "items": ["item.herbs"], "npcs": ["npc.baker"] }

5.1.3 Commande MOVE

Syntaxe : MOVE <direction>

Objectif : Déplacer le joueur vers une salle adjacente

Réponses :

  • OK room=<room-id> - Déplacement réussi
  • ERR 301 NO_EXIT - Direction invalide

5.1.4 Commande QUIT

Syntaxe : QUIT

Objectif : Fermer proprement la connexion

Réponse : OK bye

5.2 Commandes de communication

5.2.1 Commande CHAT

Syntaxe : CHAT <scope> <message>

Objectif : Envoyer un message de discussion à la portée indiquée

Portées : GLOBAL, ROOM, GROUP

Réponse : OK

5.2.2 Commande WHO

Syntaxe : WHO

Objectif : Obtenir le nombre total de joueurs

Réponse : OK players=<count>

5.3 Commandes de gestion des groupes

5.3.1 Commande GROUP CREATE

Syntaxe : GROUP CREATE

Objectif : Créer un nouveau groupe de joueurs

Réponse : OK group=<group-id>

5.3.2 Commande GROUP INVITE

Syntaxe : GROUP INVITE <username>

Objectif : Inviter un joueur dans le groupe actuel

Réponse : OK

5.3.3 Commande GROUP JOIN

Syntaxe : GROUP JOIN <leader-name>

Objectif : Rejoindre un groupe existant

Réponse : OK group=<group-id>

5.3.4 Commande GROUP LEAVE

Syntaxe : GROUP LEAVE

Objectif : Quitter le groupe actuel

Réponse : OK

5.4 Commandes d’interaction avec les ressources

5.4.1 Commande TAKE

Syntaxe : TAKE <item-identifier>

Objectif : Récupérer un objet dans la salle actuelle

Réponses :

  • OK taken=<item-id> - Objet récupéré avec succès
  • ERR 404 ITEM_NOT_FOUND - Objet indisponible

Exemple :

Client → Serveur : LOOK
Serveur → Client : OK { "room": { ... }, "items":["item.herbs"], ... }
Client → Serveur : TAKE Herbs
Serveur → Client : OK taken=item.herbs
Client → Serveur : LOOK
Serveur → Client : OK { "room": { ... }, "items":[], ... }

5.4.2 Commande DROP

Syntaxe : DROP <item-identifier>

Objectif : Déposer un objet dans la salle actuelle

Réponses :

  • OK dropped=<item-id> - Objet déposé avec succès
  • ERR 404 ITEM_NOT_IN_INVENTORY - Objet absent de l’inventaire

Exemple :

Client → Serveur : DROP item.herbs
Serveur → Client : OK dropped=item.herbs
Client → Serveur : LOOK
Serveur → Client : OK { "room": { ... }, "items":["item.herbs"], ... }

5.4.3 Commande INVENTORY

Syntaxe : INVENTORY

Objectif : Lister les objets actuellement détenus par le joueur sous forme de tableau JSON

Réponse : OK [<json-item-list>]

Exemple :

Client → Serveur : INVENTORY
Serveur → Client : OK ["item.herbs", "item.loaf_bread"]

5.4.4 Commande TALK

Syntaxe : TALK <npc-name>

Objectif : Interagir avec un personnage non-joueur

Réponses :

  • OK <dialogue> - Interaction réussie
  • ERR 404 NPC_NOT_FOUND - PNJ absent

Exemple :

Client → Serveur : TALK Baker
Serveur → Client : OK Welcome to my bakery!

5.4.5 Commande ATTACK

Syntaxe : ATTACK <npc-name>

Objectif : Engager un combat avec un PNJ ennemi

Réponses :

  • OK <combat-result> - Attaque réussie, renvoie l’état du combat
  • ERR 404 NPC_NOT_FOUND - PNJ absent
  • ERR 405 NPC_NOT_HOSTILE - Le PNJ ne peut pas être attaqué

Exemple :

Client → Serveur : ATTACK goblin
Serveur → Client : OK {"attacker_hp": 80, "target_hp": 15, "damage": 10, "status": "combat"}

5.4.6 Commande STATUS

Syntaxe : STATUS

Objectif : Obtenir les points de vie actuels et l’état de combat du joueur

Réponse : OK {"hp": <current-hp>, "max_hp": <max-hp>, "status": "<status>"}

Exemple :

Client → Serveur : STATUS
Serveur → Client : OK {"hp": 80, "max_hp": 100, "status": "healthy"}

5.4.7 Commande QUEST

Syntaxe : QUEST <npc-name>

Objectif : Demander une quête à un PNJ donneur de quêtes

Réponses :

  • OK <quest-data> - Quête disponible, renvoie les informations de la quête
  • ERR 404 NPC_NOT_FOUND - PNJ absent
  • ERR 406 NO_QUEST_AVAILABLE - Le PNJ ne propose aucune quête ou la quête est déjà terminée

Exemple :

Client → Serveur : QUEST merchant
Serveur → Client : OK {"quest_id": "fetch_herbs", "description": "Bring me 3 healing herbs", "reward": "gold_coin", "status": "available"}

5.4.8 Commande QUESTS

Syntaxe : QUESTS

Objectif : Lister toutes les quêtes actives et terminées du joueur

Réponse : OK <quest-list>

Exemple :

Client → Serveur : QUESTS
Serveur → Client : OK [{"quest_id": "fetch_herbs", "status": "active", "progress": "1/3"}, {"quest_id": "defeat_goblin", "status": "completed"}]

6. Notes d’implémentation

6.1 Travaux en cours

IMPORTANT : Cette RFC laisse volontairement certains aspects insuffisamment spécifiés afin de permettre aux équipes de développement de faire preuve de créativité dans leur implémentation. Les domaines suivants nécessitent des choix de conception et leur justification :

6.1.1 Implémentation du système de combat

Bien que les commandes de base ATTACK et STATUS soient définies, les aspects suivants sont laissés à l’appréciation des équipes chargées de l’implémentation :

  • Mécaniques de tour par tour : Gestion des tours, ordre d’initiative et gestion du temps
  • Calcul des dégâts : Formules de dégâts d’attaque, de défense et de coups critiques
  • États de combat : Début et fin du combat, et transitions entre les états
  • Commandes supplémentaires : DEFEND, FLEE, USE_ITEM ou autres actions propres au combat
  • Effets de statut : Poison, effets bénéfiques et néfastes, et gestion de leur durée

6.1.2 Implémentation du système de quêtes

Les commandes de base QUEST et QUESTS sont fournies, mais les équipes chargées de l’implémentation doivent concevoir les éléments suivants :

  • Progression des quêtes : Suivi et validation des objectifs de quête
  • Achèvement des quêtes : Mécanismes d’achèvement automatique ou manuel
  • Récompenses des quêtes : Distribution et gestion de l’inventaire
  • Dépendances entre les quêtes : Prérequis et chaînes de quêtes
  • Commandes supplémentaires : COMPLETE_QUEST, ABANDON_QUEST ou commandes similaires

Les équipes chargées de l’implémentation DOIVENT documenter leurs choix de conception et justifier l’implémentation de leurs systèmes de combat et de quêtes dans le fichier README de leur projet.

7. Système d’événements

7.1 Format des messages d’événement

Les événements sont des messages asynchrones qui informent les clients des changements d’état du monde. Tous les événements suivent le format suivant :

EVT <category> <type> <data>

6.2 Catégories d’événements

6.2.1 Événements ROOM

Type d’événementFormatDescription
PRESENCE ENTEREVT ROOM PRESENCE ENTER <username>Un joueur est entré dans la salle actuelle
PRESENCE LEAVEEVT ROOM PRESENCE LEAVE <username>Un joueur a quitté la salle actuelle
CHATEVT ROOM CHAT <username> <message>Message de discussion limité à la salle

6.2.2 Événements GLOBAL

Type d’événementFormatDescription
CHATEVT GLOBAL CHAT <username> <message>Message de discussion diffusé à l’ensemble du serveur

6.2.3 Événements GROUP

Type d’événementFormatDescription
INVITEEVT GROUP INVITE <leader>Invitation à un groupe reçue
JOINEVT GROUP JOIN <username>Un joueur a rejoint le groupe
LEAVEEVT GROUP LEAVE <username>Un joueur a quitté le groupe
CHATEVT GROUP CHAT <username> <message>Message de discussion limité au groupe

6.2.4 Événements STATS

Type d’événementFormatDescription
PLAYERSEVT STATS players=<count>Nombre de joueurs mis à jour

8. Gestion des erreurs

8.1 Format des réponses d’erreur

Les réponses d’erreur suivent le format suivant :

ERR <code> <message>

8.2 Codes d’erreur standard

CodeMessageDescription
201NAME_IN_USELe nom d’utilisateur demandé est déjà utilisé
301NO_EXITDirection de déplacement invalide
401NOT_IN_GROUPL’opération de groupe nécessite d’être membre d’un groupe
402ALREADY_IN_GROUPLe joueur appartient déjà à un groupe
404ITEM_NOT_FOUNDL’objet demandé n’est pas disponible dans la salle
404ITEM_NOT_IN_INVENTORYL’objet demandé ne se trouve pas dans l’inventaire du joueur
404NPC_NOT_FOUNDLe PNJ demandé n’est pas présent dans la salle
405NPC_NOT_HOSTILELe PNJ ne peut pas être attaqué (ce n’est pas un ennemi)
406NO_QUEST_AVAILABLELe PNJ ne propose aucune quête ou la quête est déjà terminée
900CONNECTION_FAILEDÉchec de l’établissement de la connexion
901SEND_FAILEDÉchec de la transmission du message

7.3 Récupération après erreur

Les clients DEVRAIENT mettre en œuvre des mécanismes appropriés de récupération après erreur. Les erreurs non fatales (codes 4xx) permettent de poursuivre le fonctionnement, tandis que les erreurs système (codes 9xx) peuvent nécessiter de rétablir la connexion.

8. Gestion dynamique des ressources

8.1 Unicité des ressources

TAP met en œuvre un système de gestion dynamique des ressources dans lequel les objets existent sous forme d’instances uniques dans le monde virtuel. Ce système empêche la duplication des ressources et garantit la cohérence de l’état du monde.

8.2 Cycle de vie des objets

  1. Apparu (Spawned) : L’objet se trouve dans une salle et peut être récupéré
  2. Détenu (Held) : L’objet se trouve dans l’inventaire d’un joueur
  3. Déposé (Dropped) : L’objet est déposé à nouveau dans une salle

8.3 Identification des ressources

Les ressources PEUVENT être identifiées de l’une des manières suivantes :

  • Identifiant canonique : Identifiant unique (par exemple, « item.healing_potion »)
  • Nom d’affichage : Nom lisible par un humain (par exemple, « Healing Potion », potion de soin)

8.4 Noms de ressources composés de plusieurs mots

Le protocole prend en charge les noms de ressources composés de plusieurs mots. Les clients DEVRAIENT gérer correctement les noms contenant des espaces dans leurs interfaces utilisateur.

9. Considérations de sécurité

9.1 Authentification

TAP fournit une authentification minimale fondée sur l’unicité des noms d’utilisateur. Les implémentations nécessitant une sécurité renforcée DEVRAIENT mettre en œuvre des mécanismes d’authentification supplémentaires.

9.2 Gestion du protocole réseau

Les implémentations de TAP DOIVENT gérer correctement les caractéristiques des flux TCP :

  • Fragmentation des messages : Les commandes peuvent être réparties sur plusieurs paquets TCP. Les serveurs DOIVENT conserver les messages incomplets dans un tampon jusqu’à la réception d’une ligne complète.
  • Regroupement des messages : Plusieurs commandes peuvent arriver dans un seul paquet TCP. Les serveurs DOIVENT traiter séparément chaque message terminé par un saut de ligne.
  • Encodage : Tous les messages DOIVENT utiliser l’encodage UTF-8. Les serveurs DOIVENT gérer les caractères Unicode dans les noms d’utilisateur et les messages sans erreur d’encodage.
  • Caractères de contrôle : Les serveurs DEVRAIENT rejeter les caractères de contrôle dans les messages ou les traiter de manière sûre afin de prévenir les attaques par manipulation du terminal.

9.3 Validation des entrées

Les serveurs DOIVENT valider toutes les entrées des clients afin de prévenir les attaques par injection et de garantir le respect du protocole. Les messages mal formés DEVRAIENT entraîner des réponses d’erreur appropriées.

9.4 Limites de ressources

Les implémentations DEVRAIENT imposer des limites raisonnables concernant :

  • La longueur des messages (recommandation : 1024 octets par ligne)
  • Le nombre de connexions
  • L’acquisition de ressources par joueur
  • La fréquence des messages de discussion

10. Considérations relatives à l’IANA

Ce document ne nécessite aucune action de la part de l’IANA. TAP est un protocole expérimental destiné à des fins pédagogiques et de développement.
